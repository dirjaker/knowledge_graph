# 知识图谱系统 — 技术设计文档

> **项目定位**：从文档自动构建知识图谱，支持 LLM 驱动的实体/关系抽取、可视化探索和自然语言问答的轻量级知识管理系统

> **版本**：v3.0.0 | **代码量**：~5000 行 Python + 前端 | **API 端点**：25+

---

## 一、项目背景与价值

### 1.1 为什么做

在企业知识管理中，大量非结构化文档（PDF、Word、Markdown）中的关键信息（实体、关系、事实）难以被结构化检索和推理。传统关键词搜索无法回答"张三和李四之间有什么联系"、"谁是阿里巴巴的CEO"这类关系型问题。

本项目实现了一个**端到端的知识图谱系统**，覆盖从文档解析到图谱构建、LLM 驱动的知识抽取、自然语言问答、可视化的完整链路，无需依赖外部图数据库（如 Neo4j），使用 SQLite + NetworkX 即可开箱即用。

### 1.2 面试话术

> "我做了一个知识图谱系统，v3.0 主要升级了 UI 和数据管理能力。UI 从浅色主题重构为 Neon Glow 深色科技感主题，用 SVG glow 滤镜实现霓虹发光效果。数据层新增了多文档管理，支持按文档筛选实体/关系、删除文档时级联清理关联数据。LLM JSON 解析做了三级提取+截断修复，覆盖截断、缺失逗号、附带说明文字等常见问题。前端用 Vue3 + D3.js 做交互式力导向可视化，支持 8 种霓虹色节点。整个系统用 FastAPI 提供 REST API，支持异步导入任务处理。"

#### JSON 解析策略（v3.0 新增）

LLM 输出 JSON 经常不稳定（截断、格式错误、附带说明文字），`llm_client.py` 实现了三级提取 + 两级修复：

```
原始 LLM 响应
    │
    ▼
┌─ 第一级：正则提取 ─────────────────────────┐
│  匹配最外层 { ... } 或 [ ... ]              │
│  成功 → 进入修复阶段                        │
│  失败 ↓                                     │
├─ 第二级：代码块提取 ───────────────────────┤
│  匹配 ```json ... ``` 或 ``` ... ```        │
│  成功 → 进入修复阶段                        │
│  失败 ↓                                     │
├─ 第三级：最大花括号提取 ──────────────────┤
│  找第一个 { 到最后一个 }                    │
│  成功 → 进入修复阶段                        │
│  失败 → 返回空                              │
└─────────────────────────────────────────────┘
    │
    ▼
┌─ 修复阶段 ─────────────────────────────────┐
│  _fix_json()：                              │
│    - 移除尾部多余逗号 ,} → }                │
│    - 移除注释                                │
│  _fix_truncated_json()：                    │
│    - 截断在冒号处 → 补 "unknown"             │
│    - 截断在值中间 → 闭合字符串               │
│    - 截断在数组/对象中 → 逐层闭合            │
│    - 缺失逗号 }{ → },{                      │
└─────────────────────────────────────────────┘
```

**覆盖场景**：
- 缺失逗号：`} {` → `}, {`
- 截断在冒号处：`"type":` → `"type": "unknown"`
- 截断在值中间：`"Deep` → `"Deep"`
- LLM 返回 JSON 后附带说明文字
- 尾部多余逗号：`"a": 1,}` → `"a": 1}`

### 3.3 实体抽取模块（entity_extractor.py）

**四层抽取策略**，逐层补充，去重合并：

| 层级 | 方法 | 覆盖范围 | 置信度 |
|------|------|---------|--------|
| 1 | 正则匹配 | 日期、邮箱、URL、电话、金额、版本号 | 0.8 |
| 2 | jieba 词性标注 | 人名(nr)、地名(ns)、机构(nt)、专名(nz) | 0.6-0.8 |
| 3 | 技术关键词词典 | 30+ 编程语言/框架/技术术语 | 0.9 |
| 4 | 已知实体词典 | 公司名、城市名、大学名 | 0.95 |

核心实现：

```python
class EntityExtractor:
    def extract(self, text: str, doc_id: str = "") -> list[Entity]:
        entities = []
        seen = set()

        # 1. 正则抽取（日期、邮箱、URL 等）
        for entity in self._extract_by_regex(text):
            if entity.name not in seen:
                entities.append(entity); seen.add(entity.name)

        # 2. jieba 分词抽取（人名、地名、机构名）
        if self.has_jieba:
            for word, flag in self.pseg.cut(text):
                if len(word) < 2: continue
                if flag == "nr":    # 人名
                    entity_type = EntityType.PERSON
                elif flag == "ns":  # 地名
                    entity_type = EntityType.LOCATION
                elif flag == "nt":  # 机构名
                    entity_type = EntityType.ORGANIZATION

        # 3. 技术关键词抽取（Python, Docker, 机器学习, ...）
        for tech in TECH_KEYWORDS:
            if re.search(re.escape(tech), text, re.IGNORECASE):
                entities.append(Entity(name=tech, entity_type=EntityType.TECHNOLOGY))

        # 4. 已知实体词典匹配（阿里巴巴, 北京, ...）
        for org in known_orgs:
            if org in text:
                entities.append(Entity(name=org, entity_type=EntityType.ORGANIZATION))
```

**策略二：共现分析** — 滑动窗口（2 句）内实体两两建立关系，结合实体类型推断关系类型：

```python
def _infer_relation_type(self, e1, e2, context):
    if e1.entity_type == PERSON and e2.entity_type == ORGANIZATION:
        return RelationType.WORKS_AT
    if e1.entity_type == ORGANIZATION and e2.entity_type == LOCATION:
        return RelationType.LOCATED_IN
    if e1.entity_type == TECHNOLOGY and e2.entity_type == ORGANIZATION:
        return RelationType.USES
    return RelationType.RELATED_TO
```

def get_neighbors(self, entity_name: str, depth: int = 1) -> dict:
    """BFS 获取多跳邻居"""
    queue = [(entity_name, 0)]
    visited = {entity_name}
    while queue:
        current, d = queue.pop(0)
        if d >= depth: continue
        for neighbor in self.graph.successors(current):  # 出边
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append((neighbor, d + 1))
        for neighbor in self.graph.predecessors(current):  # 入边

def find_path(self, source, target, max_depth=5):
    """最短路径，先查有向图，再查无向图"""
    try:
        return nx.shortest_path(self.graph, source, target)
    except nx.NetworkXNoPath:
        return nx.shortest_path(self.graph.to_undirected(), source, target)

### 3.7 查询引擎（query_engine.py）

**基于正则的意图识别** + **LLM 问答**，双模式互补：

```python
class QueryEngine:
    def __init__(self, graph_store):
        self._patterns = {
            "entity_info": [
                r'(.+?)是(什么|谁|哪个)',
                r'告诉我关于(.+?)的信息',
            ],
            "relation": [
                r'(.+?)和(.+?)(什么关系|有什么关系)',
            ],
            "path": [
                r'(.+?)和(.+?)(之间|中间)(有什么联系|怎么联系)',
            ],
            "neighbor": [
                r'(.+?)(认识|知道|了解)(哪些|什么)(人|组织)',
                r'(.+?)的(同事|朋友|下属|上级)是(谁|哪些人)',
            ],
        }

    def query(self, request: QueryRequest) -> QueryResponse:
        intent, params = self._parse_intent(request.question)
        if intent == "entity_info":
            return self._query_entity_info(params)
        elif intent == "relation":
            return self._query_relation(params)
        elif intent == "path":
            return self._query_path(params, request.max_hops)
        elif intent == "neighbor":
            return self._query_neighbors(params, request.max_hops)
        else:
            return self._query_search(request.question, request.top_k)
```

API 层的 `/api/query` 端点使用 LLM 问答模式：
1. 根据问题搜索相关实体
2. 收集实体的关系作为上下文
3. 将上下文 + 问题传给 LLM 生成回答

### 3.8 图算法模块（graph_algorithms.py）

基于 NetworkX 实现的图分析算法集合：

```python
class GraphAlgorithms:
    def degree_centrality(self, top_k=10):
        """度中心性 = 节点度数 / (n-1)"""
        return nx.degree_centrality(self.graph)

    def betweenness_centrality(self, top_k=10):
        """介数中心性 = 经过该节点的最短路径比例（桥梁节点）"""
        return nx.betweenness_centrality(self.graph)

    def closeness_centrality(self, top_k=10):
        """接近中心性 = 1 / 到其他所有节点的平均距离"""
        return nx.closeness_centrality(self.graph)

    def pagerank(self, top_k=10):
        """PageRank 衡量节点重要性"""
        return nx.pagerank(self.graph)

    def detect_communities(self):
        """社区发现 — Louvain 算法，回退到 greedy_modularity"""

    def get_important_nodes(self, top_k=10):
        """综合评分 = 0.4×度中心性 + 0.3×介数中心性 + 0.3×接近中心性"""

    def shortest_path(self, source, target):
        """最短路径，返回路径和边的关系类型"""

    def degree_distribution(self):
        """度分布统计"""
```

    @staticmethod
    def parse(file_path: str) -> Document:

        suffix = path.suffix.lower()
        doc_type = DocumentParser._get_doc_type(suffix)

        content = DocumentParser._clean_text(content)

    @staticmethod
    def _read_pdf(path: Path) -> str:
        import fitz  # pymupdf
        doc = fitz.open(str(path))
        return "".join(page.get_text() for page in doc)

    @staticmethod
    def _read_word(path: Path) -> str:
        from docx import Document as DocxDocument
        doc = DocxDocument(str(path))
        return "\n".join(p.text for p in doc.paragraphs)

## 四、技术亮点

### 4.1 LLM + 规则双模式抽取

v2.0 的核心升级：LLM 负责高质量抽取（DeepSeek/Ollama），规则引擎作为本地 fallback。两种模式可独立使用，也可互补。

- **LLM 模式**：通过精心设计的 prompt 实现高精度实体/关系抽取，返回结构化 JSON
- **规则模式**：四层策略（正则 → jieba → 关键词 → 词典），零依赖可运行

### 4.2 健壮 JSON 解析（v3.0）

LLM 输出 JSON 经常不稳定，v3.0 实现了三级提取 + 两级修复，覆盖截断、格式错误、附带说明文字等场景。详见 3.2 节。

### 4.3 多文档关联管理（v3.0）

- 实体和关系通过 `source_doc_ids` 字段关联来源文档
- 支持按文档筛选查看实体/关系
- 删除文档时级联清理（移除 doc_id 引用，删除孤立实体/关系）
- 首次导入真实文档时自动清除示例数据

### 4.4 异步导入任务

文档导入采用异步任务模式：
1. 创建任务（status=processing）
2. 后台线程调用 LLM 抽取
3. 前端轮询任务状态
4. 用户确认后写入图谱

避免 LLM 调用阻塞 API 响应。

### 4.5 SQLite + NetworkX 双层存储

- **SQLite** 负责持久化，WAL 模式支持并发读，外键约束保证数据完整性
- **NetworkX** 负责内存图计算，图算法直接在内存执行，O(1) 节点查找
- 启动时 DB → 内存加载，写入时双写保证一致性
- 关系重复时自动累加权重，而非重复插入

### 4.6 LLM 驱动的智能问答

`/api/query` 端点实现图谱增强问答：
1. 将用户问题作为关键词搜索相关实体
2. 收集实体的属性和关系作为上下文
3. 构造 prompt 发送给 LLM
4. LLM 基于图谱上下文生成自然语言回答

### 4.7 综合重要性评估

融合度中心性、介数中心性、接近中心性三种指标加权评分（0.4:0.3:0.3），识别图中最重要的"枢纽"节点。

### 4.8 安全加固

v3.0 的安全改进：
- 文件上传路径穿越防护（`os.path.realpath` 校验）
- CORS 限制为本地访问（可配置 `CORS_ORIGINS` 环境变量）
- API Key 部分脱敏显示，PUT 时拒绝写入脱敏值
- 配置存储在 `data/config.json`（已加入 `.gitignore`）

## 六、面试常见问题

### Q1：v3.0 相比 v2.0 有什么核心升级？

**A**：三个核心升级。第一，UI 从浅色主题重构为 Neon Glow 深色科技感主题，用 SVG glow 滤镜实现霓虹发光效果。第二，数据层新增多文档管理，实体/关系通过 `source_doc_ids` 关联文档，支持按文档筛选，删除文档时级联清理。第三，LLM JSON 解析做了三级提取+截断修复，解决了 LLM 输出不稳定的问题。

### Q2：为什么选择 SQLite + NetworkX 而不是 Neo4j？

**A**：项目定位是轻量级、零部署的知识图谱系统。SQLite 是 Python 内置的，无需额外安装数据库服务；NetworkX 是纯 Python 图计算库，图算法可以直接在内存中执行。如果数据量达到百万级节点，可以平滑升级到 Neo4j，存储层接口设计上已经预留了切换能力。

### Q3：LLM 抽取和规则抽取如何配合？

**A**：两种模式独立运行。主流程通过 LLM 抽取（`llm_client.extract_knowledge`），返回结构化 JSON。`src/web/app.py` 的 `ingest` 端点则使用规则抽取（`EntityExtractor` + `RelationExtractor`）。两者的抽取结果都经过去重和置信度评估后写入图谱。

### Q4：异步导入任务的设计思路？

**A**：LLM 调用耗时较长（可能 10-60 秒），不适合同步等待。采用 threading 后台线程处理，API 立即返回 task_id，前端通过轮询 `/api/documents/task/{task_id}` 获取状态。任务状态流转：processing → completed/failed。

### Q5：LLM JSON 解析不稳定怎么解决？

**A**：v3.0 做了三级提取+两级修复。三级提取：正则匹配最外层花括号 → 提取 ```json 代码块 → 最大花括号范围。两级修复：`_fix_json()` 处理尾部逗号和注释；`_fix_truncated_json()` 处理截断——自动补全截断的字符串、数组、对象，修复缺失逗号。同时请求 DeepSeek API 时指定 `response_format={"type": "json_object"}`。

### Q6：系统性能瓶颈在哪？

**A**：
1. **LLM 调用延迟** — 网络请求是最大瓶颈，Ollama 本地部署可缓解
2. **共现分析的 O(n²) 复杂度** — 实体数量多时两两配对开销大
3. **NetworkX 图算法** — 介数中心性复杂度 O(VE)，大图上较慢
4. **SQLite 并发** — WAL 模式支持并发读，但写入仍需锁

### Q7：如果要支持更大规模数据，架构上需要怎么改？

**A**：
1. 存储层升级到 Neo4j 或 PostgreSQL + Apache AGE
2. 引入 Celery 异步任务队列替代 threading
3. LLM 调用改为批处理模式
4. 前端分页加载图谱数据
